# Pilot procedure

1. Operator chooses one role and fills an assignment with real approvals, immutable inputs, exact files, acceptance criteria and a closing condition. No placeholder examples are admitted.
2. Confirm installed Codex supports the proposed configuration; inspect effective tools, sandbox, approval mode and inherited MCP permissions. Either establish required restrictions or record an explicitly acknowledged supervised pilot. No agent may self-approve gaps.
3. Start a fresh stage session at the repository root and provide the completed session prompt. For the first discussion pilot, use read-only shell controls with no write-capable connector access. Do not begin with a production implementation request.
4. Run the relevant COR scenarios in a disposable copy. Operator captures before/after file inventory and tool traces. No live test has been performed by merely authoring this package.
5. Validate the handoff schema; manually check approval provenance, revisions, changed-file scope, evidence and destination. Reject failed cases before advancing.
6. Close the session's assignment. Create a new assignment for the next stage, referencing the accepted handoff. Do not carry forward an old stage's exceptions or broad chat history as authority.
7. When writer roles are enabled, use a host-enforced writable area limited to assigned outputs and read-only upstream/control artifacts. If the environment cannot supply it, keep enforced mode blocked; any supervised run must name the limitation.
8. Admit parallel executor tasks only with independent ownership/isolation. The orchestrator integrates and verifies; it sends new design or code fixes back as executor assignments.

Pilot exit criterion: recorded boundary-test results for the chosen Codex configuration, plus documented limits. The authored files and static schema checks alone do not meet it.
